# Практика 3. Инверсия управления

## Цель

На основе сервиса работы с отчётами из [практики 2](../practise-2/README.md) сравнить два способа организации зависимостей: Service Locator и Dependency Injection (DI).

## Предметная область

Используйте модель отчёта и сервисы из предыдущей практики:

| Роль | Ответственность |
|---|---|
| `Report` | Данные отчёта: заголовок, дата, время и показатели продаж. |
| `ReportSaver` | Контракт сохранения отчёта. |
| `ReportSender` | Контракт доставки отчёта получателю. |
| `TextReportSaver` | Сохранение текстового представления отчёта в файл. |
| `EmailReportSender` | Отправка или имитация отправки отчёта по email. |
| `ReportService` | Основной сценарий: сохранить отчёт, затем отправить его. |

Реальная отправка почты не требуется: достаточно вывести сообщение с заголовком отчёта и адресом получателя. Реализации сохранения и отправки должны быть заменяемы.

## Часть 1. Service Locator

Реализуйте контейнер сервисов (Service Locator), который позволяет:

- зарегистрировать реализацию по контракту или ключу;
- получить зарегистрированную реализацию;
- сообщить понятную ошибку, если требуемая зависимость не зарегистрирована.

Настройте в точке запуска приложения текстовый сохранитель и email-отправитель, зарегистрируйте их в контейнере. Затем создайте `ReportService`, который получает нужные зависимости из Service Locator во время обработки отчёта.

Продемонстрируйте, что основной сценарий создаёт файл отчёта и выводит сообщение об отправке.

## Часть 2. Dependency Injection

Создайте отдельный вариант приложения с тем же предметным сценарием, но без обращения `ReportService` к Service Locator.

Зависимости `ReportSaver` и `ReportSender` должны явно передаваться в `ReportService` при его создании. В Java-реализации модуля используйте Spring IoC container: объявите компоненты или методы конфигурации, а затем получите готовый `ReportService` из контекста.

Внутри `ReportService` запрещено создавать конкретные сохранители, отправители или контейнер зависимостей. Класс должен зависеть только от контрактов.

## Сравнение подходов

1. Какие зависимости использует `ReportService` в каждом варианте?
2. Что потребуется изменить, чтобы заменить текстовое сохранение на JSON или файловую отправку на Telegram?
3. Какой из вариантов проще тестировать изолированно и почему?

## Валидация и ошибки

Проверьте входные данные в точке их использования:

- отчёт и email не должны быть пустыми или отсутствовать;
- числовые показатели отчёта не должны быть отрицательными;
- ошибка записи файла должна сохранять исходную причину.

Для прикладных ошибок используйте собственный тип ошибки или исключения. Он должен содержать код ошибки, понятное сообщение и, если применимо в выбранном языке, исходную причину.

## Запуск реализованных вариантов

Service Locator:

```shell
./gradlew :modules:practise-3:run
```

Dependency Injection со Spring:

```shell
./gradlew :modules:practise-3:runDi
```

Оба запуска выполняют один сценарий: создают отчёт, сохраняют его в
`modules/practise-3/reports` и имитируют отправку по email.

## В чём разница

**IoC (Inversion of Control)** — общий принцип: объект не собирает все свои
зависимости самостоятельно. Service Locator и DI — два способа применить этот
принцип.

В варианте **Service Locator** `Main` регистрирует реализации, но
`ReportService` сам запрашивает `ReportSaver` и `ReportSender` у локатора во
время выполнения. Поэтому по конструктору сервиса не видно, какие прикладные
зависимости ему потребуются. Ошибка конфигурации обнаруживается только при
вызове `resolve`.

В варианте **Dependency Injection** зависимости перечислены прямо в
конструкторе `ReportService`. Spring читает `ApplicationConfiguration`, создаёт
объекты и передаёт их сервису. Если объектный граф собрать нельзя, ошибка
возникает при создании контекста.

Для замены сохранения на JSON в Service Locator нужно изменить регистрацию в
`locator.Main`, а в DI — бин в `ApplicationConfiguration`. Сам сценарий
`ReportService.process` в обоих случаях остаётся без изменений.

DI проще тестировать изолированно: заглушки `ReportSaver` и `ReportSender`
можно сразу передать в конструктор. Для теста варианта с Service Locator сначала
нужно создать и правильно заполнить контейнер.

Service Locator бывает удобен для динамических плагинов и старого кода, где
реализация выбирается во время выполнения. Для обычного приложения с заранее
известным объектным графом DI обычно предпочтительнее: зависимости явные, а
ошибки конфигурации обнаруживаются раньше.
